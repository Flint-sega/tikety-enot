# 0001. Данные в SQLite, панель — один процесс без внешней БД

## Контекст

Панель — внутренний инструмент на двух-трёх операторов; критерий приёмки — «поднялось и работает из коробки» на одной машине, без внешних сервисов и без обязательных секретов. Нагрузка — единичные заявки в день плюс минутный цикл синка. Выбор стека делегирован исполнителю и утверждён владельцем.

## Решение

Заявки, пользователи, настройки и шаблоны хранятся в SQLite с журналом WAL; приложение и хранилище — один процесс и один контейнер, отдельного сервера БД нет. Схема создаётся при старте, инструмента миграций в первой версии нет.

## Почему

- PostgreSQL отдельным контейнером отвергнут: надёжнее под конкурентной записью, но добавляет второй сервис, учётные данные, том и целую категорию сбоев «БД не поднялась» — при нагрузке, для которой SQLite избыточен. Требование «работает без .env и лишних движений» с внешней БД не достигается.
- Облачная/внешняя управляемая БД отвергнута тем более: данные команды поддержки уходят с машины владельца, а у локального инструмента появляется сетевая зависимость.
- Alembic (версионирование схемы) отвергнут на старте: схема компактная, меняет её один человек, инструмент дороже разовой ручной правки. Это осознанная отсрочка, а не отрицание — при первом изменении полей вопрос вернётся.

## Последствия

- Вся история — один файл на диске: порча или потеря файла означает потерю всего; резервная копия и экспорт — обязанность владельца, панель напоминать об этом не умеет.
- Единственный писатель на уровне файла: длительные транзакции синка конкурируют с действиями операторов; WAL смягчает чтения, но не отменяет узкое место.
- Изменить схему после запуска дёшево нельзя: миграционного механизма нет, любое изменение полей — разовый скрипт либо введение полноценного инструмента.
