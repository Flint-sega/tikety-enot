# UseDesk API — спайк документации

Назначение: единственный источник фактов для `app/usedesk.py` (`UsedeskClient`). Каждый факт сверён
по официальной документации 12.10.2026; источник указан после факта. То, чего в доках нет, помечено
«не опубликовано, принято: …» — эти решения менять только через маппинг в админке (R12.6) или правку
этого файла.

Источники (официальные, проверены 2026-10-12):

- A0 Введение — https://api.usedocs.ru/article/33397
- A1 Авторизация — https://api.usedocs.ru/article/33398
- A2 Настройка API-канала (база знаний) — https://docs.usedesk.ru/article/10167
- A3 Справочник статусов — https://api.usedocs.ru/article/33728
- A4 Список запросов — https://api.usedocs.ru/article/33062
- A5 Отдельный запрос — https://api.usedocs.ru/article/33732
- A6 Создать запрос — https://api.usedocs.ru/article/33735
- A7 Обновить запрос — https://api.usedocs.ru/article/33737
- A8 Создать комментарий — https://api.usedocs.ru/article/33740
- A9 Коды ошибок — https://api.usedocs.ru/article/49506
- A10 Статус, тип и приоритет запросов (база знаний) — https://docs.usedesk.ru/article/3978

Примечание по доменам: актуальный справочник разработчика живёт на `api.usedocs.ru` (старый
`docs.usedesk.ru` вёл на 404), но базовый URL самого API для облачных аккаунтов usedesk.ru —
`api.usedesk.ru`. Домены `api.usedocs.com` и `secure.usedesk.com/uapi` для облачных аккаунтов
не используются; `secure.usedesk.ru/uapi/v1/send_file` — эндпоинт старого чат-виджета (SDK),
к тикетному API отношения не имеет (A0, https://github.com/usedesk/UseDeskSwift).

## 1. Базовый URL и формат

- Все запросы: `https://api.usedesk.ru/{method_name}` (A0).
- Только HTTPS, кодировка UTF-8, ответы в JSON (A0).
- Все методы тикетного API — **POST** (A4–A8).
- Формат дат в параметрах-фильтрах: `Y-m-d` (пример `2022-01-01`), дата-время: `Y-m-d H:i`
  (пример `2022-01-01 00:00`); времена фильтров трактуются как **UTC+0** и **включительно** (A0, A4).
- Времена в ответах — UTC+0, со секундами: `2021-04-29 11:31:23` (A4, A5).
- Для «коробочной» (self-hosted) версии URL методов отличается — уточняется в поддержке; наш случай —
  облако usedesk.ru (A4, A6, A8).

## 2. Авторизация (api_token)

- Ключ — «секретный ключ» API-канала: интерфейс UseDesk → **Каналы → Добавить канал → API**;
  Redirect URL необязателен, после сохранения появляются «ID приложения» и «секретный ключ» (A1, A2).
- Передаётся **в теле каждого POST-запроса**, имя параметра `api_token` (varchar(255), обязательный)
  (A1, A4, A6).
- Неверный токен → код ошибки 112 `invalid token` в теле ответа (A1, A9).
- Не опубликовано, принято: срок жизни/ротация ключа документацией не описаны — считаем ключ
  постоянным; хранится только в `.env` (`USEDESK_API_TOKEN`), пустой = интеграция выключена.

## 3. Формат ошибок

- HTTP-статус всегда 200; успех/ошибка различаются телом JSON (A9).
- Коды ошибок (A9): 111 server error; 112 invalid token; 113 invalid ticket_id (нет доступа у токена);
  114 invalid message; 115 access error; 116 tags must be a string; 117 invalid user_id;
  118 invalid group_id; 119 invalid client_id; 120 file size is too large (>15 МБ);
  **121 request limits — превышен лимит запросов**.
- Успешные ответы содержат `"status": "success"` (A6–A8); клиенту проверять это поле, а не HTTP-код.

## 4. Создание тикета — `POST /create/ticket`

- Путь: `https://api.usedesk.ru/create/ticket` (A6).
- Обязательные (A6):
  - `api_token` — токен API-канала;
  - `subject` — тема, строка до 255 символов;
  - `message` — сообщение, ~64 КБ, допускается HTML-разметка.
- Ответ: `{"status": "success", "ticket_id": 2154861}` — id нового тикета в поле `ticket_id` (A6).
- Значимые необязательные (A6): `client_name`, `client_email`, `client_id` (число или `"new_client"`),
  `type` (question/task/problem/incident, по умолчанию question), `priority` (low/medium/urgent/extreme,
  по умолчанию medium), `status` (число, по умолчанию 8 «Новый»), `tag`, `assignee_id`, `group_id`,
  `private_comment`, `field_id`/`field_value`, `from` (user/client/trigger), `files` (multipart).
- Не опубликовано, принято: не передаём `client_*` — UseDesk сам создаст клиента от канала; статус
  при создании не передаём (дефолт 8 «Новый» — тикет виден агентам как новый).

## 5. Комментарий и смена статуса существующего тикета

Атомарного метода «комментарий + статус» в API нет. Шов
`comment_and_set_status(usedesk_id, text, status)` — **два последовательных запроса**:

1. Комментарий — `POST /create/comment` (A8):
   - обязательные: `api_token`, `ticket_id`, `message`;
   - необязательные: `type` — `public`/`private`, **по умолчанию приватный**; `from` (`user`/`client`,
     при `user` обязателен `user_id`); `cc`/`bcc`; `files`; `user_id`;
   - ответ: `{"status": "success", "comment_id": 2154861}`.
2. Смена статуса — `POST /update/ticket` (A7):
   - обязательные: `api_token`, `ticket_id`;
   - `status` — **число-идентификатор** статуса (см. раздел 7; параметр называется `status`, не
     `status_id`);
   - метод **не умеет добавлять комментарий** (A7) — отсюда и два запроса;
   - прочие необязательные: `subject`, `priority`, `assignee_id`, `group_id`, `tag`, `user_id`,
     `silent` (`true`/`1` — отменяет автосмену «Новый» → «Открыт» при действии через API);
   - ответ: `{"status": "success"}`.

Не опубликовано, принято: комментарий закрытия в UseDesk отправляем `type=private` — это командная
пометка панели, клиенту она не адресована; порядок запросов — сначала комментарий, потом статус,
чтобы статус не «убежал» раньше текста. При сбое второго запроса — sync_state=error и повтор поллером.

## 6. Список тикетов — `POST /tickets` (шов `list_updated`)

- Путь: `https://api.usedesk.ru/tickets`, метод POST (A4).
- Фильтр по времени изменения (A4):
  - `updated_after` / `updated_before` — timestamp вида `YYYY-MM-DD HH:MM`, UTC+0, включительно;
  - аналогично `created_after` / `created_before`;
  - в ответе у тикета есть `last_updated_at` (UTC+0) и `created_at` (UTC+0) — по ним строится watermark.
- Пагинация (A4): **в ответе максимум 100 записей**; для смещения — параметр `offset`;
  «Смещение на 1 покажет следующие 100 записей», т.е. `offset` — номер страницы по 100 записей
  (offset=0 → записи 1–100, offset=1 → 101–200), шаг единица, `null` не принимает.
  Отдельных `limit`/`page` в API нет.
- Прочие параметры (A4): `fchannel`, `fassigned`, `fgroup`, `fstatus` (id статуса), `ftype`,
  `fpriority`, `client_id`, `tag`, `query` (поиск по теме/доп. полю/почте/телефону —
  **ограничение 10 запросов в минуту**), `sort` (id, status_id, client_id, assignee_id, group,
  `last_updated_at`, published_at; по умолчанию id), `order` (`asc`/`desc`, по умолчанию desc),
  `fields`, `properties`.
- Ответ — JSON-массив объектов тикета; поля: `id`, `subject`, `client_id`, `client_name`,
  `assignee_id`, `channel_id`, `group`, `created_at`, `last_updated_at`, `status` (число),
  `priority`, `type`, `last_comment`, `tags`, `ticket_fields`, `rights` (A4).
- Вызов шва: `list_updated(since)` → POST /tickets с `api_token`, `updated_after = since (UTC)`,
  `sort=last_updated_at`, `order=asc`, перебор `offset=0,1,2…`, пока страница полна (100 записей).
- Последняя активность клиентов (R12.7): список не отдаёт тексты переписки — брать
  `POST /ticket` (A5): параметры `api_token`, `ticket_id`; в ответе `comments[]`
  (`message`, `from` user/client, `published_at`), `changes[]`, `status_id`, `published_at`
  (дата создания), `last_updated_at`.

## 7. Статусы

Справочник (A3) — id, имя:

| id | Статус | Смысл (A10) |
|----|--------|-------------|
| 1 | Открыт | ждёт действий агента |
| 2 | Выполнен | работа завершена, отправлен последний ответ; новое сообщение клиента **переоткроет** тикет в «Открыт» |
| 3 | Закрыт | финален; новое сообщение клиента создаёт **отдельный новый** тикет «Новый» |
| 4 | Удален | убран из общих списков (дубль/постороннее) |
| 5 | На удержании | клиент ждёт обратной связи |
| 6 | В ожидании | агент написал и ждёт ответа клиента |
| 7 | Спам | вне статистики и фильтров |
| 8 | Новый | создан, ещё не обрабатывался |
| 9 | Рассылка | массовые рассылки, вне статистики |
| 10 | Объединен | слит с другим запросом |

- В API-доках канонический список «закрытых» не опубликован; по базе знаний из рабочей работы
  выпадают «Выполнен», «Закрыт», «Спам» (A10), «Удален» скрыт из списков, «Объединен» слит с другим.
- Не опубликовано, принято (входящий синк): закрытыми считаем **{2, 3, 7, 4, 10}**, открытыми —
  **{1, 5, 6, 8, 9}**. Сервисные статусы 4/10 относим к закрытым, чтобы заявка панели не висла
  открытой навсегда.

## 8. Rate limits

- Опубликовано: код 121 «request limits, превышен лимит запросов» без порогов (A9); поиск `query`
  в списке — не более 10 запросов в минуту (A4). Других опубликованных лимитов нет.
- Не опубликовано, принято: общий порог запросов документация не раскрывает — клиент держит
  не больше ~1 запроса/сек, при коде 121 откладывает отправку (sync_state=error, повтор
  следующим циклом поллера, 60 с). Обычная нагрузка панели (поллер + единичные мутации) порогов
  121 не достигает.

## 9. Дефолтный маппинг статусов панель ↔ UseDesk

Значения по умолчанию для редактируемого маппинга в админке (R12.6):

| Панель | → UseDesk | UseDesk | → Панель |
|--------|-----------|---------|----------|
| open (создание заявки) | статус не передаём → 8 «Новый» | 1 Открыт, 5 На удержании, 6 В ожидании, 8 Новый, 9 Рассылка | open |
| open | 1 «Открыт» (если правка вернёт открытый) | | |
| closed (закрытие с комментарием) | **2 «Выполнен»** | 2 Выполнен, 3 Закрыт, 7 Спам, 4 Удален, 10 Объединен | closed |

Почему закрытие → 2 «Выполнен», а не 3 «Закрыт»: «Выполнен» оставляет тред живым — новое сообщение
клиента переоткроет тот же тикет, и связь по `usedesk_ticket_id` сохранится; «Закрыт» перевёл бы
продолжение переписки в новый тикет с новым id, который панель не свяжет с заявкой (A10).

## 10. Сводка швов UsedeskClient → методы API

- `create_ticket(subject, message)` → `POST /create/ticket` `{api_token, subject, message}` → `ticket_id`.
- `comment_and_set_status(usedesk_id, text, status)` → `POST /create/comment`
  `{api_token, ticket_id, message, type: "private"}` → затем `POST /update/ticket`
  `{api_token, ticket_id, status}` (два запроса, не атомарно).
- `list_updated(since)` → `POST /tickets` `{api_token, updated_after, sort: "last_updated_at",
  order: "asc", offset: 0…}` с добором страниц по 100; для переписки заявки — `POST /ticket`
  `{api_token, ticket_id}` → `comments[]`.

Таймауты 10 с — из спецификации (не из доков UseDesk).
